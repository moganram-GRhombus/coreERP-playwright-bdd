1. Introduction
A critical workflow is a complete business journey that must work for the application to be useful. Testing screens one by one is not enough: the real risk lies in what happens between screens and between users. This document describes each critical workflow step by step, in plain language, with the result expected at every step.
1.1 How to read this document
ItemMeaningWhoThe person (or the system) performing the step. Coloured so that hand-offs are easy to see: Buyer, Manager, System.What to doThe action taken, written the way a human tester would do it.What should happenThe expected result. The automation turns each of these into an assertion.PhasesEach workflow is split into short phases so the story is easy to follow."To verify"Behaviour we expect but have not yet seen in the application. It is confirmed during first execution.

WF-1: Create, Submit and Approve
In simple words
Neha (buyer) needs bearings, so she prepares a purchase order for SafeGuard PPE Co. and sends it for approval. She logs out. Rahul (manager) logs in, finds the request waiting, reviews it and approves it. Everything should reflect that: the PO status, the manager's queue, and the dashboard figures.

7. WF-5: Access Control and Session Handling
In simple words
The application has one restricted area, the Approvals page. Only managers may use it. This workflow checks that the rule holds, that bad logins are refused, and that logging out really ends the session.
Part A: Role restriction
#WhoWhat to doWhat should happen1BuyerSign in as buyer and click "Approvals"."Access denied" card appears: "This page needs the manager role. You are signed in as a buyer." No Review or Approve controls are shown.2BuyerLog out. Sign in as manager and click "Approvals".Approvals page loads and shows the waiting count.Part B: Login problems
#WhoWhat to doWhat should happen3BuyerEnter username buyer with a wrong password and click Sign in.Login is refused. An error is shown and the user stays on the login screen.4BuyerEnter an unknown username with any password.Login is refused with an error.5BuyerLeave both fields empty and click Sign in.Login is refused. A message or validation prompt is shown.Part C: Logout and protected pages
#WhoWhat to doWhat should happen6BuyerSign in and click "Log out".Login screen is shown.7SystemWithout signing in again, try to open the Dashboard or Purchase orders directly.Access is refused or the login screen is shown. (To verify exact behaviour.)8. Dependencies and Data Handling
TopicDetailOrder of stepsManager actions in WF-1, WF-2 and WF-3 depend on a PO created by the buyer earlier in the same scenario. These scenarios must run in order and never in parallel.Passing the PO numberThe PO number is created by the application. Automation reads it right after submission and reuses it to find the PO later. It is never typed into the test.Shared dataThe sandbox keeps every PO created. Dashboard figures therefore drift between runs, so tests compare before and after.Two sessionsBuyer and manager each use their own browser session so one role never inherits the other's login.Clean-upCreated POs cannot be deleted. They are left in place and do not interfere because tests use their own PO number.Currency valuesDisplayed with the ? symbol and lakh grouping. They are converted to numbers before comparison.9.
