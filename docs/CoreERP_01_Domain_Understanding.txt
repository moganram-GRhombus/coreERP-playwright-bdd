2. Business Background
2.1 What is "procure-to-approve"?
Every company buys things it needs to run: raw materials, tools, safety equipment, packaging. Buying is done through a purchase order (PO), a formal document that tells a vendor exactly what the company wants, how many, and at what price. Because POs commit company money, most organisations separate the person who requests the purchase from the person who approves it. CoreERP models exactly that.
StepWhat happensWho does it1. Notice the needStock of an item runs low. The inventory screen flags it with a red "Low" badge.Buyer2. Raise a POBuyer chooses a vendor, a delivery window and the items with quantities and prices.Buyer3. Submit for approvalThe PO is sent to the manager. Its status becomes "Pending approval".Buyer4. DecideManager reviews the PO and either approves or rejects it.Manager5. OutcomeApproved POs add to the month's approved spend. Rejected POs do not.System
Why this matters for testing
The heart of the application is the hand-off between two roles. A test that only checks one screen misses the real business risk. The most valuable automated tests follow a PO from the buyer's submission all the way to the manager's decision, and then confirm the result back on the buyer's side.2.2 Glossary
TermMeaning in CoreERPPurchase order (PO)A request to buy items from a vendor. Each PO has a number such as PO-2026-0105.VendorThe supplier the goods are bought from (for example SafeGuard PPE Co.).SKUStock Keeping Unit. A unique code for each inventory item, such as SKU-1012.Line item (line)One row of a PO: an item, a quantity and a unit price. A PO can have several lines.Unit cost / Unit priceCost of one unit. In inventory it is the "unit cost". On a PO it is the "unit price", which starts at the last unit cost and can be edited.On handHow many units of an item are currently in the warehouse.Low stockAn item whose quantity on hand is below its reorder level. Shown with a red "Low" badge and a "Reorder" link.Delivery windowHow soon the vendor must deliver: 7, 14 or 30 days.Subtotal / GST / TotalSum of line totals / 18% tax on the subtotal / subtotal plus GST.DraftA saved PO that has not been sent for approval.Pending approvalA submitted PO waiting for the manager's decision.Open purchase ordersDashboard figure counting POs that are not yet decided (Draft plus Pending approval).Approved spend this monthDashboard figure: total value of approved POs for the month.Inventory valueDashboard figure: total value of stock held across all warehouses.3. These points come directly from how the application behaves and shape the design of the Playwright BDD framework.
TopicWhat we learnedHow the framework will respondElement identificationMost important elements carry stable test identifiers, and inputs also have ids.Use test identifiers first, then roles and labels. Avoid styling classes.Indexed line itemsLine fields are numbered by position (line 0, line 1 ...).The PO page object takes a line index, so any number of lines can be filled.Two rolesBuyer and manager actions alternate in one workflow.Each role logs in on its own fresh browser session; steps are reusable (Given buyer is logged in).Shared growing dataPO numbers increase; KPIs change after every run.Capture the new PO number after submission; assert on before/after differences.Currency textAmounts are displayed as ? with lakh grouping.A helper converts display text to a number before comparing.Selected stateDelivery buttons expose a pressed/not-pressed state.Assert the selected state instead of colour.Ordered workflowsManager approval needs a PO created earlier.Workflow scenarios run in order, one worker, passing the PO number between steps.Test dataUsers, vendors, items and edge values are fixed lists.Kept in separate data files, not in step code.BrowsersChromium, Firefox and WebKit are required.One project per browser in the configuration.12.1 Element reference
