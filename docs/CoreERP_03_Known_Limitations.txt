1. Purpose
No proof of concept is complete without an honest statement of what it does not yet cover, what has been assumed, and what could make results unreliable. This document lists those points so that reviewers know exactly how far the findings can be trusted and what remains to be done.
How to use this document
• Section 2 lists behaviours we have not yet seen in the application. The related test cases are marked "Verify" in the Test Scenarios workbook.
• Section 3 lists limits that come from the test environment itself.
• Sections 4 and 5 state what is excluded from this POC and how the main risks are handled.2. Open Items to Confirm

LimitationWhy it mattersHow the POC copesShared, persistent dataEvery PO created stays in the system. PO numbers and dashboard figures keep changing from run to run.Tests read the new PO number after submission and compare figures before and after, never against fixed totals.No data clean-upThe application offers no delete option, and the POC has no database or service access.Test data is created fresh each run. The sandbox may accumulate many POs over time.Order-dependent workflowsThe manager can only approve what the buyer submitted earlier.These scenarios run in sequence in a single worker. They are not suitable for parallel execution.Parallel runs collideTwo runs approving from the same queue at once may act on each other's POs.Run workflow tests on one worker; read-only tests may run in parallel.Public sandbox siteIt is a third-party site. Downtime, slowness, resets or design changes may fail tests that are not at fault.Retry on failure, keep traces and screenshots, and review failures before concluding a defect.Time-based figures"Approved spend this month" depends on the calendar. A new month may change the baseline.Spend is checked as a difference, not an absolute value.Currency formattingAmounts use the rupee symbol and lakh grouping.A helper converts text to numbers; formatting itself is checked in a few tests only.Browser differencesChromium, Firefox and WebKit may handle drop-downs and number fields differently.Tests use user-visible actions; browser-specific failures are logged as findings.Header AI coach widgetIt is paused and can overlap content.Out of scope and ignored by the tests.Login stored in the browserNot confirmed how the session is kept.Each role uses a fresh browser context to avoid mixing sessions.4. Scope Exclusions
Not covered by this proof of concept:
• Performance, load and stress testing.
• Security testing (injection, session hijacking, password policy). Only role-based access is checked.
• Accessibility, keyboard navigation and screen reader behaviour.
• Visual regression, theme switching (light/dark) and mobile or tablet layouts.
• Direct service (API) and database testing.
• Reorder flow from low-stock items, inventory sorting and pagination details.
• Continuous integration pipeline, repository hosting and demo preparation (excluded from the agreed scope).
